# Submit Transactions — Specification for BareBonesForms 2.1

Status: **ready for implementation** (spec revision 2, after reviews 13–15; section 13). Nothing implemented yet.
This is the 2.1 part of the file-upload design (`FILE-UPLOAD-DESIGN.md`, revision 7, after fifteen reviews), extracted so that 2.1 can be implemented and reviewed without reading anything about uploads. Places where 2.2 plugs in are marked **[2.2]**; nothing marked [2.2] is built in 2.1.

Further design changes should come from failing fault-injection tests (section 12), not from more paper review rounds.

## 1. Problem and goal

Today a lost response followed by a retry creates a second record and runs delivery twice. On a payment form it also creates a second Checkout session.

**Goal:** a retried submit that carries the same idempotency key within `submit_replay_ttl`
- never creates a second record,
- never runs delivery a second time,
- never reports a pending payment as done,
- and is answered even when the PHP session expired or the form definition changed or was deleted in between.

**Non-goals:** clients that send no key (plain `$_POST` without JS, API clients) keep today's behaviour; multi-server deployments; hangs below PHP (dead NFS mount, dead TCP connection that no timeout covers) — reported, not solved.

## 2. Facts about the current code this relies on

Verified in the code base:
- The submission ID is generated by the application (`'bbf_' . bin2hex(random_bytes(8))`); all four backends insert it.
- Non-payment flow: outbox init (immutable job plan) → `store()` → delivery → response. The response contains action-added fields and the delivery status, both produced **during** delivery.
- Payment flow: `store()` → `createStripeCheckout()` → session ID into record meta (`updateSubmissionPaymentMetadata`) → paid-delivery plan (`bbf_outbox_init`) → response `{submission_id, redirect}`.
- `createStripeCheckout` sends no `Idempotency-Key`, uses a 10 s timeout and ignores the HTTP status. **Its parameters are not deterministic:** `success_url`/`cancel_url` default to `HTTP_REFERER` and `HTTP_HOST`, `product_name` and `customer_email` come from the submitted data and the current definition.
- `bbf_outbox_init` is idempotent: an existing ledger is returned unchanged (`created: false`).
- Records carry `meta.definition_version`; the versions store keeps every definition blob.
- File and CSV storage lock with a **blocking** `flock` (`bbf_storage.php`). MySQL connections set no timeout.
- CSRF is an HMAC keyed by a secret in the PHP session; `session.gc_maxlifetime` defaults to 1 440 s. The honeypot field name comes from `config.php`, not from the definition.
- Checkout metadata already carries `bbf_submission_id` and `bbf_form_id`; the Stripe webhook checks them.
- Nothing runs pending outbox jobs in the background: they run inside the submit request or through a manual retry in the viewer.
- MySQL/MariaDB keep executing a statement after the client stopped waiting or died; a killed autocommit statement is rolled back unless it already committed.
- `mysqlnd.net_read_timeout` is `PHP_INI_ALL` in current PHP (checked on 8.5: access level 7, default 86 400 s, `ini_set` works); a host can still lock it with `php_admin_value`.

## 3. Files, locks and intents

```
<submissions_dir>/.submit/            global submissions_dir from config.php, never a per-form override
    .secret                           HMAC key for payload fingerprints, 0600
    <form_id>/.lock                   leaf lock for this form's intents
    <form_id>/<k>.lock                intent lock file: created once, never written, never read
    <form_id>/<k>.json                intent state: replaced atomically by the lock holder only
    <form_id>/<k>.deliver             empty marker: delivery of a complete non-payment submit may be unfinished
```
`k` = SHA-256 hex of the idempotency key. `.submit/` lives under the **global** `submissions_dir`, so step A (section 5) needs only `config.php`, the form ID and the key — no definition. Per-form storage overrides affect only the backend.

**Lock order:** transaction lock → existing storage / outbox locks → one leaf lock (`.submit/<form>/.lock` or an existing rate-limit lock). Rules:
- a process only waits for a lock later in this order than every lock it holds;
- leaf locks never nest and are never held across a backend call, a network call or a child process;
- a process holding a leaf lock may try a transaction lock only with `LOCK_EX | LOCK_NB`, never wait for it.

**Intent operations**, always under the form's leaf lock:
- **create:** `fopen(lock, 'x')`, `flock(LOCK_EX | LOCK_NB)` — uncontended by construction; a failure is a bug and fails loudly (500 + log) — write the first state, release the leaf lock;
- **take over:** open the lock file, `flock(LOCK_EX | LOCK_NB)`, release the leaf lock. Nobody can unlink the file meanwhile;
- **delete** (holding the transaction lock): unlink the state, `fclose` the lock, unlink the lock file.

**State writes:** temp file in the same directory, `fflush` + `fsync`, `rename` over the state file, directory `fsync` where PHP can open it. A failed `rename` is **not** decided by existence: the target usually exists already and holds the previous state (Review 15). After `clearstatcache()` the lock holder reads the target: bytes equal the new state → done; bytes equal the previous state and the temp file is still there → retry after 100/300/900 ms; anything else, or retries exhausted → the write failed. **A failed state write stops the operation before its next effect:** the lock is released, the request gets 503, and the next retry or recovery acts on the state that is on disk. Leftover temp files are removed by the lock holder.

**Reading a state:**
- lock file without state → treated as **no intent**. It arises when the owner died before its first state (which precedes every effect) or during intent deletion (state already gone). Both are safe: deletion happens only after `submit_replay_ttl` or together with the submission, and "no intent" gives exactly the answer a fully deleted intent gives;
- valid state → act on it;
- unreadable state (disk corruption, manual editing; the protocol cannot produce it) → **never** treated as new: the key is blocked (503), the admin is notified, `check.php` reports it, a human decides.

Only the lock holder reads a state file.

**Liveness is the lock, never age.** PHP releases locks at request end (including fatal errors and `max_execution_time`), the OS when a worker dies. A stalled but alive owner keeps its lock and nobody touches its intent. Age is used only for reporting: `check.php` lists intents locked for more than 10 minutes as "stalled".

**Platform rules:**
- Windows: `flock` is a mandatory lock; lock files are never read, state files stay readable.
- NFS: closing any handle drops a POSIX lock; the owner never opens its own lock file twice.
- **No child process, no `mail()`, no SMTP, no webhook while a lock of this design is held** — a detached sendmail could inherit the descriptor and keep the lock.
- Supported SAPIs as for BBF storage today: PHP-FPM, CGI/FastCGI, mod_php prefork. `check.php` warns on ZTS builds.

## 4. States

| State | Meaning | Written by | Next | A retry with the same key gets | Recovery does |
|---|---|---|---|---|---|
| *(no lock file)* | key never seen, or intent deleted | — | `open` | new-submission path | — |
| lock, no state | never started, or crashed while being deleted | — | deleted | treated as no intent | deletes it |
| `open` | validated; record may or may not be stored | owner | `complete`, `committed`, `aborted`, stays `open` | lock busy → 202; lock free → one inline recovery; still undecided → 503 | backend check (section 7) |
| `committed` | **payment forms only:** record stored, payment preparation unfinished | lock holder | `complete` | lock busy → 202; lock free → finish (step G), then replay; unfinished → 503 | finish (step G) |
| `complete` | record stored, response ready | lock holder | deleted after TTL / with the submission | replay (section 6) | runs unfinished delivery (`.deliver`); deletes after TTL |
| `aborted` | provably no record | lock holder | deleted | treated as no intent (new submission, **new** submission ID) | deletes after TTL |
| unreadable | corruption | — | human | 503 `submit_state_unreadable` | reports only |

State contents (all states: `v`, `state`, `submission_id`, `P`, `created`, `definition_version`, `storage_fingerprint`):
- `open` adds `deadline`, `payment` (bool), on MySQL/MariaDB `db` `{connection_id, server_started}` (section 7), and either
  - `response` `{submission_id, redirect?}` — non-payment forms; `redirect` is the form-level redirect interpolated now, or
  - `checkout` `{params}` — payment forms; **all Stripe parameters frozen now**: amount, currency, product name, resolved absolute `success_url`/`cancel_url`, metadata, customer email;
  - [2.2] the file plan.
- `committed` adds `committed_at`, `checkout` `{params}` and, once known, `session` `{id, url, expires_at}`.
- `complete` keeps only `response` `{submission_id, redirect?}` or `{submission_id, payment_unavailable: "indeterminate" | "rejected" | "expired"}`, and `session` for payment forms. Frozen parameters (they contain the e-mail address) are dropped.
- `aborted` keeps the common fields only.

Personal data in states: at most the interpolated redirect and, until `complete`, the frozen Checkout parameters. States are deleted with their submission and after `submit_replay_ttl`. No message text is stored — BBF's response message is `OK`; texts live in the client.

## 5. Request pipeline

**Step 0 — request checks that do not depend on the definition or the session:** form ID syntax, JSON body within the existing size limits, `_bbf_submit_key` absent or exactly 32 lowercase hex. A malformed key → 400. [2.2: token syntax and duplicate tokens anywhere in the body → 400.]

**Step A — look up the key** (only when a key was sent). Depends only on `config.php`, the form ID and the key: no definition load, no CSRF, no session. **Step A creates no file for a key without an intent** (Reviews 13 and 15).
1. No lock file → step B.
2. Replay rate limit: the existing rate limiter with its own bucket `replay:<k>`, `submit_replay_rate` (default 30 per minute) → 429 with `retry_after`. Polls count too. Buckets exist only for keys that have an intent, so random keys cannot create files here; they continue to step B, where CSRF and the per-IP limit apply as today.
3. Under the leaf lock, open the lock file and try `LOCK_EX | LOCK_NB`, then release the leaf lock:
   - busy → the original is still running → **202 `{status: "processing", retry_after: 2}`**;
   - no state → delete the intent → step B;
   - unreadable → **503 `{code: "submit_state_unreadable"}`**, admin notified;
   - `complete` → replay (section 6);
   - `aborted` → delete the intent → step B;
   - `open` or `committed` → recovery for this intent inline (section 7), bounded by `submit_transaction_timeout`, **once**; then `complete` → replay, `aborted` → step B, still `open` or `committed` → **503 `{code: "submit_pending", retry_after: 5}`** (Review 13).

Why before CSRF: a respondent whose session expired (default 24 min) would otherwise get a CSRF error, reload the page, get a new key and create a duplicate. Why this is safe: only the holder of the 128-bit key reaches a replay, and a replay changes nothing except the idempotent finishing of step G. A random key finds no lock file and continues to step B, where CSRF and the per-IP rate limit apply as today.

**Step B — new submission**, exactly today's pipeline: load definition (missing → 404 as today), schema check, honeypot, CSRF, per-IP rate limit, drafts branch, `validateFieldShapes` + `validate` + `collectData`, sandbox exit (sandbox opens no transaction), payment quote. [2.2: `max_files` and all other definition-dependent file checks happen here, never before step A.]

Then start the deadline (section 8), compute the submission ID, `P` (below), `definition_version`, and either `response` or the frozen `checkout` parameters. On MySQL/MariaDB open the connection `store()` will use now (never a persistent connection) and record its `CONNECTION_ID()` and the server start time (`UNIX_TIMESTAMP()` minus `Uptime` from `SHOW GLOBAL STATUS`). Create the intent in state `open`. If the lock file appeared meanwhile (a concurrent request with the same key), go back to step A.

A request without a key gets a server-generated key; the intent exists only for recovery and a retry is not recognised.

**Payload fingerprint** `P` = HMAC-SHA256 (key from `.submit/.secret`) over canonical JSON (object keys sorted recursively) of `{form ID, request body without _bbf_* fields and without the configured honeypot field}`. No definition-dependent processing, no server-derived values — an identical retry matches even after the definition changed or was deleted. [2.2: upload tokens are included as they are; the HMAC hides them.]

[2.2: steps C (plan) and D (claim).]

**Step E — store.** Non-payment forms: outbox init as today. Then `store()` within the deadline (section 8). The record meta gains `submit_key_hash` = `k`, so deleting the submission finds its intent directly. It is internal: never in CSV or JSON exports, API responses, webhook or e-mail payloads (Review 13).

**Step F — decide**, holding the transaction lock:
- `store()` succeeded → non-payment: create `<k>.deliver`, then `complete` (response from the `open` state); payment: `committed`;
- `store()` failed → `bbf_record_exists` (section 7; on MySQL only after the late-commit procedure): `exists` → as above (the existing storage-failure path already marked the outbox `attention_required`); `not_found` → `aborted` [2.2: rollback first], 503 "please submit again"; `unavailable` → stays `open`, 503.

**Step G — finish a payment** (state `committed`). Idempotent; run by the original request, by a replay and by recovery:
1. No `session` in the state:
   - now later than `committed_at` + 23 h → **no call**: Stripe keeps idempotency keys for at least 24 h only, after that the same key no longer prevents a second session (Review 15). `complete` with `payment_unavailable: "expired"`, owner notified;
   - otherwise `POST /v1/checkout/sessions` with the frozen parameters and `Idempotency-Key: bbf-checkout-<submission_id>` — **one key per submission, never changed**. The HTTP status is read (today's code ignores it):
     - 2xx → write `session` into the state;
     - no response, timeout, network error, 409 `idempotency_key_in_use` or 429 → stay `committed`, 503 "try again". Stripe saves a result under the key only after the request started executing, so the next attempt reuses the key and gets the session if one was created (429: Review 13);
     - 5xx → **indeterminate**: Stripe caches the error under the key and the session may still exist, so neither the same key nor a new one is safe (Reviews 14 and 15). `complete` with `payment_unavailable: "indeterminate"`; the owner is notified with the submission ID and the key. A session created meanwhile carries `bbf_submission_id` in its metadata and is visible in the Stripe dashboard; its URL never reached the respondent. Automatic reconciliation is a later payments feature;
     - 400 `idempotency_error` (parameters differ — possible only if the Stripe account or key changed) or another 4xx → `complete` with `payment_unavailable: "rejected"`, owner notified.
2. Session ID into the record meta if missing.
3. Paid-delivery plan: `bbf_outbox_init` with jobs prepared from the definition blob of `definition_version` and the record as stored (read back from the backend). Idempotent: an existing plan is kept.
4. Write `complete` with `{submission_id, redirect: session.url}`; the frozen parameters are dropped.

A failure in 2–3 (backend unavailable, definition blob missing) → stays `committed`, 503; the next retry or `submit-recover` finishes it.

**Step H — release, deliver, respond**, in today's order (Reviews 13 and 15): release the transaction lock (close only; the intent stays), run delivery as today, delete `<k>.deliver`, then build and send the response as today, including action-added fields and the delivery status. No lock of this design is held during delivery. Payment forms respond right after the release; their paid delivery runs from the webhook as today.

## 6. Replay

For a `complete` intent:
- **same `P`** → **200** `{already_submitted: true, submission_id, redirect?, delivery}`, where `delivery` is read from the outbox now:
  - non-payment: after replying, outbox jobs that were **never attempted** are run through the existing outbox runner (a crash between `complete` and delivery must not lose them; the outbox's leases prevent double execution when the original request is still delivering). Attempted jobs are never re-run by a replay. `<k>.deliver` is deleted afterwards;
  - payment: `payment_status` is read from the record (the effective storage config comes from the definition blob of `definition_version`, so a deleted or changed definition does not matter; blob or backend unavailable → 503 "your submission <ref> was saved; its payment status is temporarily unavailable"):
    - `paid` → success;
    - `pending` and now < `session.expires_at` → the same redirect;
    - `pending` after expiry, `failed`, or `payment_unavailable` → "your submission was saved but the payment could not be started or resumed; the organiser has been notified", owner notified once. Resuming an expired session is a later payments feature.
- **different `P`** → **409** `{code: "already_submitted_different", submission_id}`.

Action-added response fields are part of the first response only (as the existing code comment already says). Replay is 200, not 409, because CORS embeds often treat 4xx as failure. Replay never validates, never runs the per-IP rate limit and never re-runs attempted delivery.

## 7. Recovery and record existence

**Where:** inline when step A finds `open`/`committed` with a free lock; `php maintenance.php submit-recover`; opportunistically on submit requests (at most 5 intents per request, 1 s wall-clock budget).

**Per intent:** take its lock with `LOCK_NB` under the leaf lock, release the leaf lock; busy → skip, whatever the age.
- `open`, storage fingerprint differs from the current configuration → treat as `unavailable`;
- `open`, record `exists` → non-payment: `<k>.deliver`, then `complete`; payment: `committed`, then step G;
- `open`, record `not_found` (on MySQL only after the late-commit procedure below) → `aborted`, `<k>.deliver` deleted if present; an outbox ledger created for that submission ID is marked `attention_required` exactly like today's storage-failure path (no delivery runs for it);
- `open`, `unavailable` → skip, report; nothing changes;
- `committed` → step G;
- `complete` with `<k>.deliver` older than the outbox lease time → after releasing the intent lock, run the never-attempted jobs through the existing outbox runner, then delete the marker (Review 13). Without this, a crash between `complete` and delivery would lose the notification unless the respondent retried. The outbox claim ensures each job runs at most once even if the original request is still delivering; the age only keeps recovery from running jobs out of order while a live original is between two jobs;
- `complete` / `aborted` older than `submit_replay_ttl` → delete (with any marker).

Opportunistic recovery and `submit-recover` find work by listing `.deliver` markers and intent state files; the opportunistic budget covers both.

`bbf_record_exists($config, $form, $id): 'exists' | 'not_found' | 'unavailable'` — file: directory readable → present or not; CSV: strict read, lock or parse failure → `unavailable`; SQLite/MySQL: connect failure, timeout or any query exception → `unavailable`. Bounded by the deadline like `store()`.

**Late commit on MySQL/MariaDB** (Reviews 13 and 15). A client timeout does not stop the server: an `INSERT` waiting for a metadata lock (for example behind a hosting backup's `FLUSH TABLES WITH READ LOCK`) can commit after PHP gave up or died. An immediate `not_found` would then abort the intent, the retry would get a new submission ID, and the late `INSERT` would create a second record — with uploads, rollback would also take files from a record that later appears. So, before `not_found` is trusted, the original statement is ended from a new connection:
1. server start time differs from the one in the `open` state by more than 5 s → the server restarted and the statement is gone; go to step 4. This also keeps the kill from hitting an unrelated connection that reuses the ID after a restart;
2. `KILL CONNECTION <connection_id>` — a user may kill its own connections without `SUPER` or `PROCESS`. Success or error 1094 (unknown thread) → continue; any other error → `unavailable`;
3. poll every 100 ms until `information_schema.PROCESSLIST` has no row with that ID — a killed statement rolls back first and stays visible meanwhile; still visible when the deadline passes → `unavailable`;
4. look up the record.

The server-side timeouts are shorter than the client's (section 8), so the server normally gives up first with a definite error; the kill is the backstop. SQLite, file and CSV writes run inside the PHP process and end with it.

**Storage fingerprint:** backend name plus resolved location (file/CSV: `realpath` of the directory; SQLite: `realpath` of the database; MySQL: SHA-256 of host, port, database, table). `not_found` is trusted only with a matching fingerprint. It guards against configuration changes, not against a database restored from an older backup. The docs tell operators to run `submit-recover` before changing storage settings; `check.php` reports intents with a foreign fingerprint.

## 8. Deadline

`submit_transaction_timeout` (default 30 s) starts right before the intent is created (on MySQL before the store connection is opened) and covers **everything** until the state is decided: lock waits, `store()`, the existence check after a failed `store()` including the late-commit procedure, and step G. On Linux `max_execution_time` counts CPU time only, so every wait needs its own bound (`r` = remaining seconds):
- **MySQL:** `PDO::ATTR_TIMEOUT` = `min(5, r)` for connect; `ini_set('mysqlnd.net_read_timeout', r)` before connecting, return value checked (a host may lock it; `check.php` reports the effective value); per session `SET SESSION innodb_lock_wait_timeout = s` (row locks) **and** `SET SESSION lock_wait_timeout = s` (metadata locks — default one year; a hosting `mysqldump` with `FLUSH TABLES WITH READ LOCK` or an `ALTER TABLE` blocks an `INSERT` there). On MariaDB also `SET SESSION max_statement_time = s`, which covers writes; MySQL's `max_execution_time` covers only `SELECT` and is not used. `s = max(1, r − 2)`: the server gives up before the client (Review 13). Each `SET` is best effort: a failure is logged, not fatal. No persistent connections.
- **SQLite:** busy timeout = `r`.
- **File and CSV:** inside a transaction the storage locks are taken with `LOCK_EX | LOCK_NB` in a loop (50 ms sleeps) until the deadline; a timeout takes the normal `store()` failure path. Outside transactions they stay as today.
- **Stripe:** HTTP timeout `min(10, r)`.
- Deadline passed before `store()` starts → `aborted`, 503 "please submit again".

`ignore_user_abort(true)` for the duration of a transaction. The deadline is a **target verified by integration tests** (section 12), not a proven guarantee: a dead TCP connection where `net_read_timeout` could not be set, or a hang below PHP, is a documented residual risk shown by `check.php` as "stalled".

## 9. Deletion and TTL

- Deleting a submission (viewer, API, retention) deletes its intent and marker: the path follows from `meta.submit_key_hash`. A locked intent is skipped and expires with the TTL. Records from before 2.1 have no intent.
- `complete` and `aborted` intents are deleted after `submit_replay_ttl` (default 24 h). A retry after that is a new submission — a documented limit.
- Retention batches: at most 500 submissions per batch and a 20 s wall-clock budget per HTTP-triggered run; unfinished work continues on the next run. The CLI uses no time budget.

## 10. Client (`bbf.js`)

- Key: 128 bits from `crypto.getRandomValues`, generated when the form renders, sent as `_bbf_submit_key` in the JSON body; every retry of the same fill reuses it.
- After a successful submit a new key is generated **before** any redirect or navigation, and again on `pageshow` with `event.persisted === true` when the last submit succeeded (back-forward cache).
- 403 CSRF on the new-submission path (session expired) → fetch a fresh CSRF token once and retry with the **same** key.
- `202 processing` → automatic retry after `retry_after`, up to 5 times; then "Your submission is still being processed. Please don't fill in the form again — try Submit again in a few minutes; it will not create a duplicate." The key is kept.
- `200 already_submitted` → handled exactly like a first success (including `redirect`).
- `409 already_submitted_different` → "This form was already submitted (reference …). Changes made after that were not saved."
- `429` → wait `retry_after`, same key. `503 submit_state_unreadable` → "We could not confirm your submission. The organiser has been notified." Other 503 → "Please submit again" with the same key.
- Budget: a few hundred bytes gzipped.


`maintenance.php submit-recover`: runs recovery for all forms, prints what it did and what it skipped.

## 12. Interruption and fault-injection tests

| 29 | MySQL: kill refused (privilege error) or thread still listed at the deadline | `unavailable`; stays `open`; nothing deleted |
| 30 | 10 000 requests with random keys | no file created for a key without an intent before the per-IP limit |
| 31 | crash after `complete`, before delivery, no retry | `submit-recover` runs each never-attempted job exactly once; marker deleted |
| 32 | payment: Stripe 429 | same key; stays `committed`; 503; the next retry gets the session |
| 33 | payment: `committed` older than 23 h without a session | no Stripe call; `payment_unavailable: "expired"` |
| 34 | `open` with backend `unavailable`, reached through step A | exactly one inline recovery, then 503 `submit_pending`; no loop |
| 35 | CSV/JSON export, API response, webhook and e-mail payload | contain no `submit_key_hash` |

## 13. Review log

**Reviews 13–15 (spec revision 1 → 2).** Review 13 and Review 15 read this spec; Review 14 saw only the upload design's review log.

Adopted:
- **State replacement decided by content, not existence** (Review 15, point 1): a failed replace with the old target still present was treated as success.
