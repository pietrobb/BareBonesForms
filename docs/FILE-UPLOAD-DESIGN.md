# File Uploads — Design Proposal (revision 7, after fifteen reviews)

Status: **implementation landed for BareBonesForms 2.2**, built on the submit transactions of **2.1**. This document preserves the reviewed design and its pre-implementation context; for current setup and operating instructions, see [README — File Uploads](../README.md#file-uploads) and [the user guide](../docs.html#file-uploads).
**2.1 is specified separately in [`SUBMIT-TRANSACTIONS.md`](SUBMIT-TRANSACTIONS.md)** (frozen for implementation): locks and intents, states, the submit pipeline, replay, recovery, deadline, client key handling and their tests. This document covers only what uploads add; references like "spec §5" point there.
Revision 7 incorporates reviews 13–15. Most of them concern the 2.1 spec (`SUBMIT-TRANSACTIONS.md`, section 13 there); this document gains two protocol rules: a failed claim undo keeps the transaction `open`, and paths of an unresolved write-ahead entry are off limits to new claims and user deletion. What changed and why is listed in section 15.

## 1. Context reviewers need

BareBonesForms (BBF) is a zero-dependency PHP 8.1+ form engine for **shared hosting**: no Composer, no build step, no database required. One form = one JSON file in `forms/`. Relevant existing architecture:

- `bbf.js` renders the form and submits **JSON** (`Content-Type: application/json`) to `submit.php?form=ID`. `submit.php` also accepts `$_POST`.
- Pipeline in `submit.php`: load definition → schema check → honeypot → CSRF (session HMAC; skipped for allowlisted CORS origins) → per-IP rate limit → drafts branch → `validateFieldShapes` + `validate` + `collectData` (hidden-by-`show_if` fields are excluded) → sandbox exit → payment quote → **delivery outbox init (immutable job plan)** → `store()` → run delivery jobs (email / webhook / custom actions, retryable from the viewer).
- **Payments (Stripe):** the record is stored with `payment_status: pending`, *then* a Checkout session is created (`POST /v1/checkout/sessions`, parameters derived from the definition, config and submission ID; BBF sets no `expires_at`, so Stripe's 24 h default applies; no `Idempotency-Key` today; `success_url`/`cancel_url` default to `HTTP_REFERER`/`HTTP_HOST`, so today's parameters are **not** deterministic), its ID written into the record's meta, a paid-delivery plan prepared, and the client receives `{submission_id, redirect}`. Today a lost response followed by a retry creates a second record.
- **The submission ID is generated by the application** (`'bbf_' . bin2hex(random_bytes(8))`) before outbox init and `store()`. All four backends insert that ID; none uses autoincrement IDs.
- Four storage backends: file (one JSON per submission, `flock` + temp file + atomic `rename`), SQLite, MySQL/MariaDB (JSON columns), CSV (append-only, already has reserved `__bbf:*` columns for definition versioning). Storage can be overridden per form; per-form state such as the delivery outbox lives under the effective `submissions_dir` (`.delivery/`).
- **BBF already depends on `flock`** for file storage, CSV, rate limits, the delivery outbox and backup restore. The outbox already separates a stable lock file (`<ledger>.lock`) from the ledger it rewrites, and its critical sections are brief — delivery does not run inside them. Restore holds a per-form lock (`.<form>.restore`) for the whole run. BBF assumes one web server (no multi-node shared storage).
- Network timeouts today: Stripe HTTP 10 s, SMTP socket 10 s, webhooks 5 s. MySQL connections set **no** timeout.
- `submissions/`, `logs/` etc. are denied by `.htaccess` (and documented nginx rules); `check.php` verifies this with real HTTP probes using sentinel files. `submissions_dir` can be moved outside the web root. The retention archive and backups already default to `dirname(__DIR__)/barebonesforms-private/…`.
- **Backup and restore are CLI-only** (`maintenance.php`). A backup is one JSON bundle per form. Restore requires an **empty target** (no definition, no records, no versions/review/outbox for that form), writes everything unpublished, and **publishes the form definition last**; records are unreachable until then.
- The viewer authenticates API calls with a session-bound token sent in the `X-BBF-Viewer-Token` header, never in the URL. The editor sandbox already requires an authenticated principal.
- Deleting a form in the editor removes only its definition; its submissions stay. There is no form rename.
- Client IP is `REMOTE_ADDR` everywhere; BBF has no trusted-proxy support. The existing submit rate limiter names its files `md5(ip)`.
- Emails are currently single-part `text/html` via `mail()` or the built-in SMTP client. There is no MIME multipart code yet.

## 2. Goals and non-goals

**Goals**
- 2.1: **A retried submit never creates a second record and never misreports the state** (in particular, a pending payment is never shown as done). Applies to every form, with or without files, for requests that carry the same idempotency key within the replay window.
- 2.2: A `file` field type: one or more files per field, required/optional, conditional like any other field.
- **Default mode:** uploaded files live outside every web-served directory. A weaker, explicitly opted-in mode exists for hosts where that is impossible (section 7), documented as weaker.
- Works with all four storage backends, with retention, backup/restore, deletion and the viewer.
- **No visible record ever references a missing file** (except after an explicit operator action such as restoring a database without its uploads, section 10). **No file is deleted without positive proof** that it is unreferenced: a transaction that provably did not commit, a recorded deletion intent, or an explicit operator command.
- Upload tokens and viewer tokens never appear in a URL.
- No new dependencies. Uses only extensions that are almost always present; degrades loudly when one is missing.
- Uploads are **off** until the operator enables them in `config.php`.

**Non-goals (2.2)**
- Virus scanning, image processing, public file URLs, direct-to-S3, chunked/resumable uploads (> ~50 MB), files inside repeatable groups, files in respondent drafts (section 4.8), email attachments, inline preview in the viewer, multi-server deployments. Several are in phase 3 (section 13).

## 3. Threat model

| Threat | Mitigation |
|---|---|
| Remote code execution: attacker uploads `shell.php` / `x.php.jpg` / `.htaccess` / `.user.ini` and requests it by URL | Default storage is outside the web root (section 7). Client filename never used on disk; stored name is random hex with no extension. Hard-denied extensions (section 6) cannot be enabled. In the opted-in web-root mode: own `.htaccess`, a random subdirectory name, and a live HTTP probe that blocks uploads when the directory is reachable. That mode **does not guarantee** behaviour of a web server configured to execute every file (section 7). |
| Stored XSS via HTML/SVG/polyglot files opened in the browser | Downloads only through an authenticated endpoint, always `application/octet-stream` + `Content-Disposition: attachment` + `nosniff` + `CSP: sandbox` + `Cross-Origin-Resource-Policy: same-origin`. SVG and HTML hard-denied. No inline preview (phase 3 requires re-encoding, section 13). |
| Path traversal via filename / field name / IDs | Stored path built only from validated IDs (`[a-zA-Z0-9_-]`) + random hex; containment checked with `realpath`. Original name kept only as sanitized metadata. |
| Header / CSV / JSON injection via the original filename | Name sanitized at upload time, including after truncation (section 8); CSV cells pass `csvSanitize`; `Content-Disposition` built from a stripped ASCII fallback plus RFC 5987 `filename*`. |
| Disk and inode exhaustion | Capacity ledger with owned reservations under the uploads lock: per-file, per-submission, per-IP staging bytes and entries, global staging, global stored bytes **and stored file count**, minimum free disk (section 9). Staging TTL 2 h. |
| Token theft / reuse | Upload token is a 128-bit secret bound to form + field; stored only as a hash; travels only in request bodies; single use, enforced by the claim under the uploads lock (section 4.3). |
| Token leakage through logs, history, `Referer`, statistics | No token in any URL (sections 4.2, 10). |
| Form used as a malware relay | 2.2 sends **no attachments**. Later only on the owner `notify` email, never on `confirm_email`. |
| MIME spoofing, fake or macro-enabled Office files | Extension allowlist **and** `finfo` **and**, for Office/ODF, a bounded structural plausibility filter with `ZipArchive` (section 6). This filter is not a proof of validity or of the absence of active content. |
| Crash, stall or lost response in the middle of a submit, restore or deletion | Every multi-step operation has a lock file held until it decides and a state file replaced atomically; recovery acts only on operations whose lock it can take and only on a positive answer from the backend; all I/O inside a submit transaction has a deadline (section 4; spec §3, §8). |
| Retry after a lost response (double record, false "paid", duplicate Checkout session) | Submit transactions of 2.1: key looked up before the definition, CSRF and validation; keyed payload fingerprint; replay returns the current state and next step; frozen Stripe parameters with per-attempt idempotency keys (spec §5–§6). |
| Personal data lingering | Staging TTL 2 h; committed transaction state reduced to IDs and a keyed fingerprint and deleted with the submission; deletion on submission delete / retention; archive without file bytes by default; no files in drafts; IP stored only as a keyed HMAC. |
| Decompression bombs | Nothing is decompressed; Office checks read the ZIP central directory with entry-count and byte limits. |

Residual risks stated in the docs: files are not scanned for malware. An attacker with many IP addresses can fill the global staging quota and block uploads (not the disk, not other form features) for up to one staging TTL. Behind a CDN or reverse proxy all visitors share one IP, so per-IP limits act as global limits (section 9). A process that hangs below PHP (for example on a dead NFS mount) keeps its lock; its operation stays "processing" until the operator restarts PHP (`check.php` reports it, spec §3).

## 4. Upload flow, transactions and recovery

**Why two-phase, not one multipart submit.** A single `multipart/form-data` submit could only keep files after a validation error by staging them server-side — the same machinery plus a forked pipeline. It cannot show per-file progress, and when a large file pushes the request over `post_max_size`, PHP delivers empty `$_POST` and `$_FILES`, losing the text answers too. Two-phase keeps each request small, keeps the submit body unchanged, and sidesteps `max_file_uploads` and `max_execution_time`.

### 4.1 Locks, intents and lock order

The submit transaction lock, intent format (stable lock file + atomically replaced state file), liveness by lock, platform rules and deadline are defined in spec §3 and §8 and apply unchanged. Uploads add:

| Lock | Kind | Protects | Held |
|---|---|---|---|
| per-form restore lock `.<form>.restore` (existing) | operation | one restore run and its state `<uploads_dir>/restore/<form>.json` | whole restore |
| submit transaction lock (spec §3) | operation | one submit | until the state is decided; released before delivery |
| deletion lock `<uploads_dir>/deleting/<batch>.lock`, state `<batch>.json` | operation | one deletion batch | whole batch |
| reservation lock `<uploads_dir>/staging/.incoming-<r>.lock` | operation | one upload request, from reservation to publish | one upload request |
| existing storage, CSV, versions, review and outbox locks | existing | as today | brief critical sections |
| `<uploads_dir>/.lock` | leaf | uploads tree and ledger: reservations, publish, claim, rollback, user delete, GC, file unlinks, recount, creating and deleting deletion and reservation intents | briefly |
| `.submit/<form>/.lock`, existing rate-limit locks | leaf | spec §3; as today | briefly |

**Lock order:** per-form restore lock → at most one other operation lock → existing storage/outbox locks → one leaf lock; the rules of spec §3 (wait only for later locks, leaf locks never nested nor held across backend/network/child processes, operation locks only tried with `LOCK_NB` under a leaf lock). Deletion and reservation intents are created, taken over and deleted under the uploads lock with the procedure of spec §3; the restore state's liveness is the per-form restore lock.

### 4.2 Upload

When the user selects a file, `bbf.js` sends it alone (`multipart/form-data`, one file per request, `XMLHttpRequest` for progress) to `submit.php?form=ID&action=upload&field=NAME`. The URL carries only public identifiers. The CSRF token travels in the `X-BBF-CSRF` header, so it survives a `post_max_size` overflow.

Server steps, in this order:
1. Uploads enabled and storage location allowed (section 7).
2. Upload rate limit per IP. It reads nothing from the body, so **every request counts**, including ones rejected in later steps.
3. `CONTENT_LENGTH` vs `post_max_size` → **413** before anything reads `$_POST` / `$_FILES`.
4. CSRF from the header (same rules as submit).
5. Form exists, field exists, is `type: file`, allowed in this form version.
6. Exactly one file under `$_FILES['file']`, not an array, no other file keys; otherwise 400.
7. PHP upload error code (each `UPLOAD_ERR_*` mapped to a clear message).
8. Name sanitization (section 8), size, extension, content type (section 6) — checked on PHP's own temporary file.
9. Under the uploads lock: capacity check and **owned reservation** — create and lock `staging/.incoming-<r>.lock`, add `{r, kind: "upload", bytes, ip_hmac, created}` to the ledger (section 9). The ledger write is `fsync`ed before step 10.
10. `move_uploaded_file()` into `staging/.incoming-<r>` (outside the lock; this may be a cross-filesystem copy). The request keeps holding its reservation lock.
11. Under the uploads lock: **publish** — write `staging/<hash>.json`, rename `.incoming-<r>` → `staging/<hash>` (rename outcome rule, 4.5), replace the reservation with a staging entry, delete the reservation intent. On any failure the incoming file is unlinked; **only after a successful unlink** is the reservation removed and its intent deleted. A failed unlink keeps the reservation, whose owner lock is released at request end, so GC removes both later (section 9).

Response: `{ "token": "<32 hex>", "expires_at": "<ISO 8601>", "file": { "name", "size", "type" } }`.

`action=upload_delete` (user clicked ×) is a POST with the token in the JSON body. Under the uploads lock: the entry must exist, belong to this form and not be listed in an unresolved write-ahead entry (otherwise 503 with `retry_after`, section 9); bytes unlinked, metadata deleted, ledger reduced by the bytes actually unlinked. An unlink failure leaves bytes without metadata, still counted, for GC.

Deployment note (Review 7): PHP and the web server buffer the whole request body before `submit.php` runs. The docs recommend a web-server body limit (`client_max_body_size` in nginx, `LimitRequestBody` in Apache) close to `post_max_size`.

### 4.3 What uploads add to the submit transaction

The pipeline is spec §5. Uploads plug in at the marked places:
- **Step 0:** token syntax (32 hex) and no duplicate token anywhere in the body → 400. Nothing definition-dependent.
- **Step A:** unchanged. A replay never touches staging, never re-checks files and never looks at `max_files`, so a retry after the operator lowered `max_files`, removed the field or changed its type still gets its replay (Review 11).
- **Step B:** `max_files`, field existence and `type: file` are checked here, with the other definition-dependent validation. `P` covers the body as received, tokens included (spec §5).
- **Step C — plan.** For each token read `staging/<hash>.json`; record in the `open` state the list `{token_hash, file_id, staging metadata}` and the target directory `<form>/<submission_id>/`. Recovery can restore every entry exactly.
- **Step D — claim**, one critical section under the uploads lock:
  - every entry present (bytes + metadata), unexpired, not listed in an unresolved write-ahead entry of another owner (otherwise 503 with `retry_after`, tokens stay valid; section 9), same form and field, and valid against **the definition used for this submit** (field visible, extension in the current `accept`, size within the current `max_size`, per-submission total within limit);
  - the ledger admits the move (stored bytes and file count after the move within the caps);
  - **write-ahead ledger entry** (section 9) listing this transaction and its paths, `fsync`; exclusive `mkdir` of the target directory; rename every entry into it (rename outcome rule); delete their staging metadata; final ledger write that removes the write-ahead entry.
  Any failure inside the section undoes its own moves before releasing the lock. **Only a confirmed complete undo** marks the transaction `aborted`: validation → 422 "please upload the file again"; capacity → 507; transient rename failure → 503 "temporary storage problem, try again" (tokens stay valid). If the undo itself fails, the write-ahead entry stays, the transaction stays `open`, the request gets 503, and recovery finishes the undo (4.4) (Reviews 14 and 15).
- **Step E:** descriptors go into the record.
- **Step F:** `not_found` (on MySQL only after the late-commit procedure, spec §7) → rollback (4.4) before `aborted`. A failed rollback leaves the transaction `open`.
- **Committed state:** the file plan (names, `ip_hmac`, staging metadata) is dropped in the same write that leaves `open`.

### 4.4 Rollback and recovery

**Rollback** (from step F or from recovery), one critical section under the uploads lock while the transaction lock is held: write-ahead ledger entry for this rollback (section 9); for each planned entry in the target directory, rewrite `staging/<hash>.json` from the copy in the state, then rename the bytes back to `staging/<hash>`; entries that already expired are unlinked instead; `rmdir` the target directory; final ledger write. Missing entries (for example removed by a concurrent deletion of an `exists` record) are skipped. **If rollback fails, the transaction stays `open`** and recovery retries it.

**Recovery** is spec §7, with two additions: `open` + `not_found` runs the rollback before `aborted` (files go back to staging while unexpired, so the respondent's retry with the same key succeeds); a write-ahead ledger entry naming a transaction is resolved only by that transaction's recovery (section 9).

### 4.5 Rename outcome rule

A failed `rename()` does not always mean "not moved": an NFS client may retransmit a rename the server already executed and receive `ENOENT`; on Windows an antivirus scanner can hold a fresh file open and cause a sharing violation. Every target is a fresh path, so after a failed `rename()` the code calls `clearstatcache()` and decides by existence:
- target exists → the move happened; continue;
- source exists, target does not → transient; retry up to 3 times (100, 300, 900 ms), then treat as failure of the whole section (503, undo, tokens stay valid);
- neither exists → impossible under the lock; stop, leave the intent `open` for recovery, log an error.

This applies to publish, claim, rollback and the restore move, whose targets are fresh paths. **It does not apply to replacing a state file**, whose target already exists: that is decided by comparing the target's content with the new state (spec §3; Review 15).

### 4.6 Replay and record existence

Spec §6 and §7. For uploads: a `409 already_submitted_different` means files uploaded for the changed attempt are never claimed and expire from staging.

### 4.8 Sandbox and drafts

**Sandbox:** the upload endpoint in sandbox mode requires the same authenticated principal as sandbox submits today. It validates the file and discards it and returns `sbx.<payload>.<hmac>` (form, field, name, size, type, expiry) signed with a key derived from `<uploads_dir>/.secret`. Sandbox submits accept only valid, unexpired `sbx` tokens; production submits reject them. Sandbox submits open no transaction.

**Drafts** never store file fields. `draft_save` removes every `type: file` field server-side (the client does not send them either); restoring leaves file fields empty; the draft controls show "Files are not saved in drafts. Attach them before you submit."

## 5. Form definition

```json
{
    "name": "cv",
    "type": "file",
    "label": "Your CV",
    "required": true,
    "accept": [".pdf", ".docx"],
    "max_size": "5MB",
    "max_files": 1,
    "show_if": { "field": "apply", "value": "yes" }
}
```

- `accept`: extensions, each in the server allowlist (definition error otherwise). Default: the configured set. The HTML `accept` attribute gets both extensions and MIME types.
- `max_size`: per file; integer bytes or `KB` / `MB` suffix, **binary** (1 MB = 1024² bytes). Effective value `min(max_size, config, upload_max_filesize, post_max_size − 64 KB)` is sent to the client.
- `max_files`: default 1; `> 1` renders `multiple`.
- Not allowed inside a repeatable group in 2.2.
- A newer form version may narrow `accept`/`max_size` or remove the field; staged files are re-checked at submit (4.3 step D). A replay is not re-checked (spec §5 step A).
- `form.schema.json`, `validateFormDefinition`, `smoketest.php` updated.

## 6. Type validation

Operator-configurable allowlist, each extension mapped to accepted `finfo` MIME types:

| Default on | Extensions |
|---|---|
| yes | `pdf`, `jpg`/`jpeg`, `png`, `webp`, `gif`, `txt` |
| yes, **only when `ZipArchive` is available** | `docx`, `xlsx`, `odt`, `ods` |
| opt-in | `heic` (to be confirmed on a device whether iOS Safari converts to JPEG), `csv` (formula injection in Excel), `zip`, `doc`/`xls` (legacy OLE) |
| **hard-denied, cannot be enabled** | Server-side: `php*`, `phtml`, `phar`, `pht`, `shtml`, `cgi`, `pl`, `py`, `sh`, `asp*`, `jsp`, `inc`. Browser-active: `html`, `htm`, `xhtml`, `xht`, `svg`, `svgz`, `xml`, `xsl`, `xslt`, `js`, `mjs`, `swf`. Server config: `htaccess`, `user.ini`. Windows: `exe`, `dll`, `bat`, `cmd`, `com`, `scr`, `msi`, `msc`, `jar`, `vbs`, `vbe`, `jse`, `ps1`, `wsf`, `wsh`, `hta`, `cpl`, `pif`, `reg`, `scf`, `lnk`, `url`. macOS: `app`, `dmg`. Macro Office: `docm`, `xlsm`, `pptm`, `dotm`, `xltm`. Disk images: `iso`, `img`, `vhd`, `vhdx`. |

The hard-deny list is a backstop; the real control is the narrow allowlist plus isolated storage.

**Office Open XML and ODF: structural plausibility filter.** `ZipArchive` opened read-only (`ZipArchive::RDONLY` where defined), reading only the central directory, never extracting, bounded:
- `numFiles` checked first: at most 2 000 entries; names read one at a time with `getNameIndex` inside that bound, no list built in memory;
- `docx`: `[Content_Types].xml` and `word/document.xml` present; `xlsx`: `[Content_Types].xml` and `xl/workbook.xml` present; `vbaProject.bin` anywhere → rejected (a renamed `.docm`/`.xlsm`);
- `odt`/`ods`: a `mimetype` entry present whose content (read with a 100-byte limit) equals `application/vnd.oasis.opendocument.text` / `.spreadsheet`; entries under `Basic/` or `Scripts/` (ODF macros) → rejected. Position and compression of `mimetype` are not checked — that adds no security (the server never opens the document) and would reject files from generators other than LibreOffice.
- A `.docx`/`.xlsx` that `finfo` reports as `CDFV2` is an encrypted (password-protected) Office file: rejected with "Encrypted documents cannot be uploaded. Please remove the password and try again."

The docs name this a **plausibility filter**: it rejects common disguises and macro containers, it does **not** prove that a document is valid or free of active content (external links, DDE fields, embedded objects).

Without `ZipArchive` the four extensions are removed from the effective allowlist, a form that accepts them gets a clear upload error, and `check.php` / `smoketest.php` report it. If `fileinfo` is missing, uploads are refused and `check.php` reports it.

## 7. Storage location and on-disk layout

**Default:** `uploads.dir` = `dirname(__DIR__) . '/barebonesforms-private/uploads'`. No automatic fallback into the web root.

On every upload request the resolved `uploads.dir` is compared with the BBF install directory and `realpath($_SERVER['DOCUMENT_ROOT'])`. If it is inside either:
- uploads are refused unless `'allow_inside_web_root' => true`;
- with that flag, `diagnostic_base_url` must be set; on first use BBF creates one random subdirectory `data-<16 hex>` and keeps everything below it (exactly one `data-*` entry is allowed, otherwise uploads are refused);
- the upload endpoint runs the HTTP sentinel probe, cached for 1 hour under a lock and keyed by the resolved path. A reachable sentinel **or** an unverifiable probe blocks uploads with 503 and notifies the admin. The message distinguishes the two: "Upload directory is publicly reachable at <url> (HTTP 200)" versus "Probe could not reach <url>: <error>. The server may not be able to reach its own domain (firewall, NAT). Set diagnostic_base_url to an address the server can reach."

The docs describe that mode as weaker: protection depends on server rules that can change after the probe. The document **does not guarantee** the behaviour of a misconfigured server: a server set to execute every file in a directory regardless of extension (`SetHandler`, `ForceType`, an nginx location passing everything to PHP-FPM) could execute uploaded content. The operator must also not map `uploads.dir` into the web via an alias, symlink or virtual host — that cannot be detected from PHP.

```
<uploads_dir>/                       (in web-root mode: <dir>/data-<16 hex>/)
    .htaccess                        "Require all denied" (defence in depth)
    .secret                          HMAC key material, 0600
    .lock                            the uploads lock (section 4.1)
    .quota.json                      capacity ledger incl. reservations, rewritten via temp file + rename under .lock
    staging/
        <sha256(token)>              file bytes, no extension
        <sha256(token)>.json         {form, field, name, size, type, sha256, file_id, created, expires_at, ip_hmac}
        .incoming-<r>                upload being written (outside the lock, reserved)
        .incoming-<r>.lock           held by the uploading request (liveness of the reservation)
    deleting/
        <batch>.lock, <batch>.json   deletion intent (section 10)
    restore/
        <form>.json                  restore state; liveness = existing per-form restore lock (section 10)
        <form>.tmp/                  files being restored
    <form_id>/<submission_id>/
        <file_id>                    file bytes, no extension (file_id = "f_" + 16 hex)

<submissions_dir>/.submit/            spec §3 (global submissions_dir)
    .secret
    <form_id>/.lock, <form_id>/<k>.lock, <form_id>/<k>.json
```

- Staging, restore and final directories live under the same root, so every move is a same-filesystem `rename()`.
- Directories `0750`, files `0640` where the platform allows.
- Staging entries are named by the token **hash**; a listing reveals no usable token.
- Submission directories contain only file bytes. Revision 4's `.delete-intent` inside them is gone: deletion intents live in `deleting/` and are batched, which also removes the Windows problem of `rmdir` on a directory with an open intent.
- `ip_hmac` = HMAC-SHA256 of the client IP with a key derived from `.secret`; a plain hash of an IPv4 address is reversible by brute force.

## 8. What goes into the submission record

The field value is a list of descriptors; never a path, never the token:

```json
"cv": [
    { "id": "f_3fa9c1d2e4b5a6f7", "name": "Jana Novak CV.pdf", "size": 184233,
      "type": "application/pdf", "sha256": "…" }
]
```

- File, SQLite and MySQL store this unchanged (JSON).
- **CSV:** the field column holds a readable cell (`Jana Novak CV.pdf (180 KB)`) through `csvSanitize`; the reserved column `__bbf:files` holds the full descriptors as JSON, keyed by field. The record is the single source of truth for descriptors.
- `name` is sanitized **at upload time**, so it can never fail `json_encode` later: invalid UTF-8 replaced (`mb_scrub`; without `mbstring`, if the name fails `preg_match('//u')`, every byte ≥ 0x80 becomes `_`); basename only; control characters and bidi overrides removed; NFC if `intl` is available. **Truncation to 200 bytes keeps the extension and cuts the stem on a character boundary** (`mb_strcut`; without `mbstring`, trailing bytes are dropped until the string is valid UTF-8 again), then appends `…` before the extension. Validity is checked again after truncation.
- Email templates (`_summary`, `{{cv}}`): names and sizes, HTML-escaped. No links in 2.2.
- Webhooks and custom actions: descriptors. Helper `bbf_upload_path($config, $formId, $submissionId, $fileId)` for custom actions; the docs state that actions **only read** these files and must never move, change or delete them.

## 9. Capacity limits and garbage collection

**Capacity ledger.** `.quota.json` under the uploads lock holds staging bytes/entries (total and per `ip_hmac`), stored bytes, stored file count, and a list of **reservations** `{r, kind: "upload" | "restore", bytes, ip_hmac, created}`. Rules:
- an upload **reserves** before writing to disk (4.2 step 9); the claim reserves final capacity in the same critical section as the move (4.3 step D); a restore reserves its stored bytes and files before copying (section 10);
- every reservation has an owner whose liveness is a lock: the upload's `.incoming-<r>.lock`, or the per-form restore lock;
- bytes are released from the ledger **only after they are actually unlinked**; a failed unlink keeps them counted until GC succeeds;
- per-IP entries that reach zero are removed on every write;
- **write-ahead accounting** (Review 11): the ledger must never show less than what is on disk, even after a crash between moving files and updating the ledger. Every critical section that moves or creates bytes (publish, claim, rollback, restore move) first writes the ledger **charging both the old and the new location** plus a write-ahead entry `{op, owner, paths}` (`owner` = transaction `k`, reservation `r` or restore form), `fsync`, then moves, then writes the exact ledger without the entry. After a crash the ledger over-counts, which can refuse an upload but never exceeds a limit. A write-ahead entry is resolved by whoever next holds its owner's lock (transaction recovery, a dead reservation's cleanup, restore recovery) with a recount of exactly the listed paths; until then GC and recounts **leave the listed paths alone**, and a claim by another transaction or an `upload_delete` of a listed path gets 503 with `retry_after` (Reviews 14 and 15). Example: a rollback moved bytes back to staging and the process died before the final ledger write; without this rule a new submit could claim the file while the old entry is still open, and the two accountings would overlap;
- **before refusing an upload because of a staging limit, staging is recounted** under the lock and the decision is made again: published entries from `staging/` (at most 2 000) plus every reservation whose owner is alive, **at its full reserved size**, whatever has been written so far (Review 8). A reservation whose owner lock can be taken is dead: its incoming file and lock file are removed and the reservation dropped. Leaked reservations from crashed requests therefore cannot block uploads on a host without cron;
- the stored part is recounted by `check.php` and `maintenance.php uploads-cleanup`, under the lock. All moves and unlinks in the uploads tree happen under that lock; the only writes outside it are `.incoming-*` files and `restore/<form>.tmp/` copies, both covered by a live reservation, so a scan can neither miss a moving file nor count it twice.

| Limit | Default |
|---|---|
| `max_file_size` | 10 MiB |
| `max_submission_size` | 25 MiB |
| `max_staging_bytes` / `max_staging_entries` | 500 MiB / 2 000 |
| `per_ip_staging_bytes` / `per_ip_staging_entries` | 100 MiB / 40 |
| `max_stored_bytes` / `max_stored_files` | 5 GiB / 50 000 |
| `min_free_disk` (after this file) | 200 MiB |

Hitting a global limit notifies the admin once per day; `check.php` warns at 80 % of `max_stored_bytes` and `max_stored_files`. The docs explain that `min_free_disk` measures the whole server disk, not the hosting account quota — `max_stored_bytes` and `max_stored_files` are the real protection, and shared hosts often limit inodes to 100–250 thousand for the whole account. If `disk_free_space` is disabled, the `min_free_disk` check is skipped with a `check.php` warning.

Per-IP limits use `REMOTE_ADDR`, like the existing rate limiter. Behind a CDN or reverse proxy they act as global limits; the docs say so. Trusted-proxy support is a general BBF gap (phase 3).

Documented limitation: PHP writes the request body to its temp directory before any of this code runs; that is bounded only by `post_max_size` and the web server (4.2, deployment note).

**Garbage collection** (opportunistic on upload requests, plus `php maintenance.php uploads-cleanup`), under the uploads lock:
- staging entries past `expires_at` (TTL 2 h): bytes unlinked, then metadata, ledger updated;
- **inconsistent staging pairs in either direction** (bytes without metadata, metadata without bytes): deleted, **unless a write-ahead entry lists the path** — a crash inside publish, claim or rollback leaves exactly such a pair, and only the owner's recovery may resolve it (Review 11). Every other legitimate transition happens inside one critical section under the same lock, so no grace period is needed;
- `.incoming-*` files: removed only when their reservation's owner lock can be taken, or when no reservation exists for them (reservation, lock file and ledger entry are created in one critical section, so that cannot arise inside the protocol). No age rule (Review 8);
- transactions: only through recovery (4.4);
- final directories: deleted **only through a deletion intent or `restore-abort`** (section 10). A directory with neither a record nor an intent is **reported, never deleted** — it means something outside the protocol happened (manual file operations, a database restored without its uploads) and needs a human. Forms with an unfinished restore are skipped in this report.

## 10. Viewer, export, deletion, retention, backup

- **Viewer:** shows names and sizes. A download is a hidden `<form method="post" target="<hidden iframe>">` to `viewer.php?action=file` with form, submission ID, file ID and the viewer token in the **POST body**. A successful download is an attachment and leaves the viewer page intact; an error response loads into the iframe, whose `load` event makes the viewer read the error and show it. The token needs `read` on the form; the file ID must appear in that record's descriptors. Before streaming: output buffers closed, `zlib.output_compression` off, `set_time_limit` raised where allowed. Headers: `Content-Type: application/octet-stream`, `Content-Disposition: attachment; filename="<ASCII fallback>"; filename*=UTF-8''<percent-encoded>` (CR, LF, `"` and `\` removed first), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer`, `Cache-Control: private, no-store`, `Content-Length`; streamed with `readfile`. Access goes to the access audit log.
- **Export:** CSV gets names; JSON export gets descriptors. No ZIP-of-all-files in 2.2.
- **Deletion** (viewer delete, API delete, retention), inside the existing coordinated deletion (`bbf_outbox_delete_submissions`), **batched** (Review 9): one intent per deletion call, and retention splits large runs into batches of up to 500 submissions with a 20 s wall-clock budget per HTTP-triggered run; the rest continues on the next run (Reviews 11 and 12).
  1. under the uploads lock, create the deletion intent `deleting/<batch>` with state `{form, submission_ids, storage_fingerprint, created}` — only IDs that have an upload directory — one `fsync` per batch;
  2. delete the records and their outbox, as today, and their transaction intents, found directly through `meta.submit_key_hash` (spec §9; Review 12); a locked one is skipped and expires with the replay window;
  3. unlink the files in chunks of up to 200 per uploads-lock critical section, with ledger updates;
  4. remove the directories and delete the intent.
  A failure after step 1 never blocks the record deletion; leftovers are finished by cleanup. **Cleanup** handles an intent only when it can take its lock, per listed ID: record `not_found` with matching fingerprint → finish steps 3–4; record `exists` → the deletion never reached that record, so drop the ID from the intent and keep its files; `unavailable` → skip the whole intent.
- **Form deletion in the editor:** removes only the definition, as today; files follow their submissions.
- **Payments:** a record stored before checkout is an ordinary record; abandoned payments keep their files under the same deletion and retention rules. Shorter retention for unpaid records is a general gap, listed in phase 3.
- **Retention:** the dry run reports file count and bytes; the digest covers file IDs. The archive contains descriptors and hashes only unless `retention.archive_files => true`, which **requires** `retention.archive_files_days`. The viewer shows "file removed by retention" instead of an error.
- **Backup** (CLI only, as today): the JSON bundle gains descriptors with SHA-256; file bytes go to a sidecar directory `<bundle>.files/<submission_id>/<file_id>`, copied with `stream_copy_to_stream` and hashed while copying — never loaded into memory or embedded in JSON. The existing "capture twice and compare" check also compares the descriptor lists.
- **Restore** (CLI only; target must be empty as today, now including `<uploads_dir>/<form>/`, so a submission ID can never collide). The whole run holds the existing per-form restore lock, which is also the liveness of the restore state. Files first, then the publish point:
  1. dry run: every sidecar file present and its hash correct, capacity available;
  2. under the uploads lock: **reserve** the stored bytes and file count (`kind: "restore"`, ledger `fsync`ed), **then** write the restore state `restore/<form>.json` `{phase: "files", files, reservation}`. A crash between the two leaves a restore reservation without a state; its owner (the per-form restore lock) is free, so it is dead and is dropped (Review 11);
  3. copy the files into `restore/<form>.tmp/`, verifying each hash after the copy (outside the uploads lock, covered by the restore lock and the reservation);
  4. under the uploads lock: rename `restore/<form>.tmp` → `<form>` (rename outcome rule), turn the reservation into stored usage, state `phase: "records"`;
  5. restore records, versions, review and outbox **unpublished**, exactly as today;
  6. publish the form definition — the existing publish point; records become reachable with their files already in place;
  7. remove the restore state.

  **Recovery of an unfinished restore** (only when the per-form restore lock can be taken): definition published → remove the state; `phase: "files"` → no record exists yet, so remove the files (from `.tmp` or `<form>/`), release the reservation, remove the state; `phase: "records"` → **nothing is deleted automatically**, because unpublished records may reference the files (Review 9). It is reported with the command `php maintenance.php restore-abort <form>`: dry run first, then with confirmation it removes the unpublished records, versions, review data, outbox, files and state of that form together. It refuses when the definition is published. Until then the leftovers stay unreachable: the viewer, the API and delivery retries resolve a form through its published definition — a test confirms this for each of them.
- **Restoring a database from a hosting backup** without the matching uploads is outside BBF's control: records may reference files that no longer exist (the viewer shows "file missing") and directories may exist without records (reported by cleanup, never deleted). The docs recommend BBF form backups, which contain both.
- **Outbox retries:** jobs reference file IDs; a file deleted before a retry fails the job permanently with `file_missing`.

## 14. Test plan

2.1: spec §12 (`tests/review-submit-transaction-test.php`). 2.2: new `tests/review-upload-test.php` + extensions, using the same fault-injection hook.

Highest priority — crash, stall, concurrency, retry. A fault-injection hook (tests only) can stop the process **between every two steps** of each protocol **and inside every state write** (after the temp file is written, after `fsync`, after `rename`):
- **Submit transaction with files:** death after every step of 4.3 C–D and of the rollback, including after the first of several renames; then recovery and a retry with the same key. Every run ends with either one record + all its files or no record + the files back in staging (or expired).
- **Replay with files (Review 11):** a retry after `max_files` was lowered, the file field removed, or its type changed → replay 200, never 422.
- **Accounting after a crash (Review 11):** crash inside publish, claim, rollback and the restore move after the write-ahead write → the ledger over-counts, never under-counts; parallel claims after the crash never exceed a cap; GC leaves the listed paths alone; the owner's recovery resolves the entry with exact numbers. Crash between the restore reservation and the restore state → reservation dropped as dead. Injected unlink failure in 4.2 step 11 → the reservation stays until GC removes the file.
- **Rollback race:** rollback of submit A interleaved with a claim of the same tokens by submit B; B's state is never overwritten.
- **Unresolved write-ahead paths (Reviews 14 and 15):** crash after a rollback moved bytes to staging, before the final ledger write; a claim by another key and an `upload_delete` of that token get 503 until the owner's recovery resolves the entry, then succeed with exact accounting. Injected failure of the claim undo → transaction stays `open`, never `aborted`; recovery finishes the undo.
- **Rename outcomes:** injected `rename()` failure with the target present (NFS retransmit) → treated as success; with the source present (sharing violation) → retries, then 503 with valid tokens; on Windows CI with a real file held open.
- **Deletion:** death between every two deletion steps; cleanup finishes or reverts correctly per ID; database restored to an older state (record reappears) → cleanup drops the ID and keeps the files; directory without record and without intent → reported, never deleted; deleting a submission removes its transaction intent; retention of 5 000 submissions finishes in one run with a bounded number of `fsync`s.
- **Restore:** death between every two restore steps, then recovery, then a full restore; a published record never lacks a file; `phase: "records"` leftovers → nothing deleted automatically, `restore-abort` removes records and files together and refuses on a published form; the viewer, the API and delivery retries cannot reach unpublished leftovers; a restore concurrent with uploads never exceeds the stored caps; hash mismatch and missing sidecar file fail the dry run.
- `store()` returning false with the record written, not written, and backend down; backend unavailable during GC, recovery and cleanup → nothing deleted; storage fingerprint changed → recovery deletes nothing and `check.php` reports it.
- **Ledger:** parallel uploads and claims at every limit → never exceeded; **recount while an incoming file is partially written → its full reservation kept**; recount with a dead owner (lock free) → reservation, incoming file and lock removed; process killed after reservation → the next refusal triggers a staging recount and the upload succeeds; injected unlink failure → bytes stay counted until GC removes them; stored recount during parallel claims matches reality.

Other:
- Request shape: `post_max_size` overflow → 413; rate limit counts the 413; CSRF only from `X-BBF-CSRF`; two files, `file[]`, extra keys → 400; duplicate token in one field or across fields → 400.
- Tokens: other form, other field, reused, expired, forged, sandbox/production mix-ups; sandbox upload without an authenticated principal → refused; no token in any URL the client builds.
- Definition drift between upload and submit → 422.
- Drafts: `draft_save` with tokens stores none; restore leaves file fields empty.
- Names: `../../x`, NUL, invalid UTF-8, bidi override, 1000-byte multibyte name (valid UTF-8 after truncation, extension kept), `CON.pdf`, `=HYPERLINK(…).pdf` in CSV, CR/LF and quotes in `Content-Disposition`.
- Types: PHP as `.jpg`, HTML as `.pdf`, SVG, polyglot JPEG+PHP, plain ZIP as `.docx`, `.docm` as `.docx`, ZIP with 5 000 entries, ODF with wrong `mimetype`, `.ods` as `.odt`, ODF with `Basic/` macros, ODF with compressed or non-first `mimetype` from another generator (**accepted**), password-protected `.docx` (clear message), Office without `ZipArchive`.
- Limits: boundary sizes, `"5MB"` = 5 242 880 bytes, `max_files`, per-submission total, per-IP bytes, stored bytes and file count, free disk, `disk_free_space` disabled → warning.
- Location: inside web root without the flag → refused; with the flag and a reachable directory → refused; unreachable probe → distinct message; changing `dir` forces a new probe; `data-*` subdirectory created once.
- Conditional: hidden required file field does not block submit.
- Client: failed optional upload blocks submit; expiry warning; 202 auto-retry; same key reused on manual retry; new key after reset.
- All four backends: store, read, export, delete, retention (with and without `archive_files`), backup with sidecar files, restore.
- Download: headers; buffering and compression off; token only in the POST body; error shown via iframe; `read` permission; file ID not in the record → 404; audit entry.
- `ip_hmac` differs from a plain hash and is stable per install.
- Manual, on a device: iOS Safari with `accept` not listing HEIC delivers JPEG.

- *"Ready for production", "guaranteed deadlock-free"* (Review 7): the scenarios of Reviews 8 and 9 (torn state write, recount under a live upload, lost Stripe answer, replay after a definition change, existing locks missing from the order) were real.
- *`GET /v1/checkout/sessions/{id}` when only the URL is missing* (Review 9): cannot happen — ID, URL and expiry are written together in one atomic state write before the meta.
- *`expires_at` derived from the record's creation time* (Review 9): BBF sends no `expires_at`, so the parameters are already deterministic; the rule "no current time in parameters" is written down for future changes.
- *`fsync` behaviour on Windows* (Review 7): noted; shared hosting targets are Linux, and the protocol's correctness does not depend on durability across power loss on Windows.

### Revision 5 → 6 (reviews 10, 11 and 12)

Review 10 approved revision 5 as final. Reviews 11 and 12 found concrete gaps and both recommended freezing the design after them and moving to implementation with fault-injection tests. That is the plan.

**Adopted**
- **Step A depends only on `config.php`, the form ID and the key** — before the definition load, CSRF, session and validation; `max_files` and all file checks moved to the new-submission branch; `P` is an HMAC over the body as received, tokens included; a deleted or changed definition still gets its replay, never a new submission (Review 11, point 1; Review 12, point 1). `.submit/` moved under the global `submissions_dir` so the lookup needs no definition.
- **`committed` (record stored) separated from `complete` (response ready)** for payment forms, with an idempotent finishing step run by the original request, replay and recovery: session into meta, paid-delivery plan, response (Review 11, point 3). Non-payment forms precompute their response in the `open` state, so recovery can complete them directly; never-attempted delivery jobs are run after such a recovery.
- **Stripe:** per-attempt keys `bbf-checkout-<id>-<n>`, spent on 5xx, kept on timeouts (Review 12, point 2) — **withdrawn in revision 7**: one key per submission, 5xx ends as `payment_unavailable` (Reviews 14 and 15). While checking this, today's parameters turned out **not** to be deterministic (`success_url`/`cancel_url` default to `Referer`/`Host`): all parameters are now frozen in the state before the first call. Revision 5's claim that they were derived only from definition, config and record was wrong.
- **Deadline:** `lock_wait_timeout` for metadata locks, MariaDB `max_statement_time`, `LOCK_NB` loops for file/CSV storage, lock waits and the post-failure existence check inside the deadline; the deadline is described as a target verified by tests (Review 12, point 3; Review 11, 16.3).
- **Replay rate limit** per key (Reviews 11 and 12, point 4).
- **`submit_key_hash` in record meta** instead of scanning intents on deletion (Review 12, point 5).
- **No message text in states**; personal data in states limited and listed (Review 12, point 6).
- **Separate 2.1 specification with a state table and an interruption test matrix** (Review 12, point 7; Review 11's closing remark).
- **Write-ahead accounting** in the capacity ledger; GC leaves paths of unresolved entries alone; restore reserves before writing its state; reservation removed only after a successful unlink (Review 11, point 2).
- Per-form leaf lock `.submit/<form>/.lock`; `LOCK_NB` when creating an intent; "lock without state" after a crashed deletion documented as intended; ledger `fsync` before `move_uploaded_file`; time budget for batches (Review 12, minor points and 16.1, 16.4; Review 11, 16.1, 16.4).

**Not adopted, with reasons**
- *"Nothing to criticise, 100 % ready", "server-side timeouts are unnecessary"* (Review 10): the metadata-lock wait, the Stripe error caching, the non-deterministic Checkout parameters and the CSRF/session replay failure were real.
- *`mysqlnd.net_read_timeout` is `PHP_INI_SYSTEM`* (Review 12, 16.3): on current PHP it is `PHP_INI_ALL` (checked on 8.5: access level 7, `ini_set` succeeds). A host can still lock it, so the return value is checked and `check.php` reports the effective value, as Review 12 suggested.

### Revision 6 → 7 (reviews 13, 14 and 15)

Changes to the 2.1 protocol are listed in spec §13: state replacement decided by content, MySQL late commit handled by kill-and-wait before `not_found`, no new Stripe key after 5xx, replay limiter only for existing intents, delivery before the response, recovery of delivery lost after `complete`.

**Adopted here**
- Claim undo: `aborted` only after a confirmed complete undo; a failed undo keeps the transaction `open` (Reviews 14 and 15). §4.3 D now matches §4.4.
- Paths of an unresolved write-ahead entry are off limits to claims by other transactions and to `upload_delete`, not only to GC and recounts (Reviews 14 and 15).
- The rename outcome rule applies only to fresh targets; state replacement uses spec §3 (Review 15, point 1).
